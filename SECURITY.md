# Security Policy

A2AWall is a policy enforcement point for agents exposed over A2A. This document describes
which versions receive fixes, how to report a vulnerability, and what is explicitly out of
scope.

## Supported Versions

| Version | Supported |
|---------|-----------|
| 0.2.x   | Yes       |
| < 0.2   | No        |

A2AWall is pre-1.0 and maintained by one person. Only the latest 0.2.x release receives
security fixes. There are no backports to earlier lines.

## Reporting a Vulnerability

Report privately through GitHub private security advisories:

https://github.com/nebullii/a2awall/security/advisories/new

Do not open a public issue or pull request for a suspected vulnerability. Do not disclose it
on social media or a mailing list before the timeline below has run.

A useful report includes:

- affected version or commit
- the module or entry point involved, for example `src/security/admission.ts`
- a minimal reproduction: the request, the configured policy, and the observed decision
- the security property you believe is violated
- the impact you believe follows from it

### Timeline

| Stage | Target |
|-------|--------|
| Acknowledgement of the report | 5 business days |
| Initial assessment and severity | 10 business days |
| Fix or documented mitigation, and public disclosure | 90 days from acknowledgement |

These are targets, not guarantees. If a fix will take longer than 90 days the reporter is
told why and a revised date is agreed. Credit is given in the advisory unless the reporter
asks otherwise.

## Scope

In scope:

- bypass of gateway admission control in `src/security/admission.ts` and
  `src/security/middleware.ts`: a request that the configured policy should reject but that
  the gateway admits
- incorrect capability, scope, trust-tier, or approval-gate evaluation
- bypass of the message-size limit, or other unbounded resource consumption reachable from a
  single unauthenticated or low-privilege request
- trust-label confusion in `src/context/envelope.ts` or `src/context/trust.ts` that lets
  untrusted content be labelled as trusted
- incorrect policy evaluation in `src/runtime/sandbox.ts`, `src/validation/output.ts`,
  `src/memory/store.ts`, `src/retrieval/policy.ts`, or
  `src/orchestration/delegation.ts`: the evaluator returns allow where the policy says deny
- credential or token leakage into logs, error responses, or the agent card
- vulnerabilities in the published `a2awall` package contents or in its direct dependencies

Out of scope:

- the `demo/` directory, which is example integration code and not part of the published
  package
- the `docs/` site, which is static content
- findings that require an attacker to already hold a valid high-trust credential, unless the
  finding is a privilege escalation beyond what that credential grants
- reports generated by a scanner with no demonstrated impact on A2AWall's own behaviour
- low and moderate advisories in transitive development dependencies that are not reachable
  at runtime

## Non-Goals and What Is Not a Vulnerability

The following are known, intentional properties of A2AWall as it currently stands. Reports
describing them as vulnerabilities will be closed as working as documented. They are listed
here so the boundary is explicit rather than implied.

### 1. `dev-token` is a development fixture, not an auth mechanism

The static bearer credential `dev-token` appears in `.env.example` and as the default
identity token in `defaultSecurityPolicy` in `src/security/policy.ts`. It exists so that
`npm test`, `node dist/smoke.js`, and the quick-start commands in the README run without
configuration.

It is a fixture. It is a published, well-known string. It is not a production
authentication mechanism and it is not treated as a secret. A deployment that keeps it is
unauthenticated in practice.

Reporting that `dev-token` is guessable, hardcoded, or present in the repository is not a
vulnerability report. A finding that the gateway accepts `dev-token` after the operator has
configured a different token, or that the shipped default is used even when
`SECURITY_BEARER_TOKEN` is set, is in scope, because that is a policy evaluation bug.

### 2. A2AWall provides no protection if the wrapped agents are directly reachable

A2AWall is a policy enforcement point. It sits in front of agents and decides which
requests reach them. It has no control over any path that does not pass through it.

If a caller can open a connection to a wrapped agent directly, every control in this
project is bypassed: admission, capability scoping, trust tiers, size limits, and audit.
The agent answers as it would to any client.

Ensuring that agents are reachable only through the gateway is a deployment
responsibility. Bind agents to loopback or a private network, put them behind a network
policy or security group that admits only the gateway, and do not publish their addresses
in discovery. A report that an agent bound to a public interface can be reached without a
token describes the deployment, not A2AWall.

### 3. "Implemented foundation" means policy evaluation, not runtime isolation

`SECURITY_ROADMAP.md` marks several phases as "implemented foundation". That phrase means a
policy module exists and can evaluate a decision. It does not mean the decision is bound to
runtime execution, and it does not mean anything is contained.

Specifically, A2AWall does not provide process sandboxing, container isolation, seccomp or
similar syscall filtering, filesystem or network namespacing, or memory isolation between
tenants at the operating-system level. `src/runtime/sandbox.ts` evaluates whether an action
is permitted by policy. It does not confine a process that performs one.

A report that agent code can read the filesystem, open a socket, or exhaust memory despite
`src/runtime/sandbox.ts` being present is not a vulnerability in A2AWall. Isolation of that
kind must come from the runtime the agent executes in. Bugs in the evaluators themselves,
where a policy that denies an action is evaluated as allow, are in scope and are covered
above.

## Hardening Guidance

For a deployment that handles anything real:

- replace every value in `.env.example`, starting with `SECURITY_BEARER_TOKEN`
- give each caller a distinct identity and the narrowest capability and scope set that works
- keep agents off any interface the gateway does not need
- terminate TLS in front of the gateway; A2AWall does not do it
- treat approval gates and risk metadata as signals for your own review process, not as
  enforcement of a downstream system's permissions
- enforce least privilege in the downstream systems the agents call, independently of the
  gateway
